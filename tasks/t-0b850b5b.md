## Description

Surfaced by the t-24594c4a fresh-eyes audit (2026-06-28). `MiniAppAgentSession` (scarf/scarf/Features/Projects/MiniApp/MiniAppAgentSession.swift) spawns its ACP client via the default factory `{ ACPClient.forMacApp(context: $0) }` (line ~53) — NO `projectCwd` — yet sets the ACP `session/new` cwd to the project root (`newSession(cwd: projectRoot)`, line ~145). This is the exact process-cwd vs session-cwd split that t-565f8d45 / t-24594c4a fixed for chats: mini-app agent sessions resolve TOOL dirs against the project but do NOT load the project's AGENTS.md/CLAUDE.md (Hermes reads context files from the PROCESS cwd). The class docstring ("cwd = project root") is now misleading — it conflates the two cwds.

NOT a clear-cut fix — it intersects t-42db11e9 (untrusted project context-file injection). Mini-apps run untrusted / agent-generated web content that drives the agent via `scarf.prompt`; auto-injecting the project's AGENTS.md/.cursorrules into that agent session is a BIGGER prompt-injection surface than an interactive chat the user explicitly opened. So this is a DESIGN decision, not a reflexive one-liner.

Decide one of: (a) thread `projectCwd: projectRoot` into the factory default here too (one line) so mini-app agents get full project context — only if t-42db11e9 lands a trust gate first; (b) leave process cwd = home (no AGENTS.md for mini-apps) as a deliberate trust-minimizing choice, and FIX the docstring to say "ACP session cwd = project root; process cwd intentionally home — AGENTS.md not loaded for mini-app agent sessions (trust)". Either way the misleading docstring must be corrected. Pairs with t-42db11e9.
