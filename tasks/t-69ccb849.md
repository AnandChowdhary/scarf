## Description

Surfaced by the projects-integration fresh-eyes audit (2026-06-27).

`FleetApplyExecutor.applyCron` (scarf/scarf/Features/Projects/ViewModels/FleetApplyExecutor.swift:183) forwards `--deliver all` to target hosts unconditionally when copying a source project's `[proj:]` cron jobs across the fleet. But `deliver=all` is a v0.14+ value (`HermesCapabilities.hasCronDeliverAll = atLeastSemver(0,14,0)`). On a pre-v0.14 TARGET host in a mixed-version fleet, `hermes cron create --deliver all` errors → the copied job FAILS (non-fatal: the executor reports it in the result, but the job isn't created). Same-version / single-host fleets are unaffected.

Fix: resolve the target `ctx`'s HermesCapabilities (version probe via `ctx.runHermes(["--version"])` → parse), and when `job.deliver == "all" && !target.hasCronDeliverAll`, either drop `--deliver` (fall back to default delivery) or mark that field `.skipped` with a "target too old for deliver=all" message. Plain `--deliver <platform>` is baseline — leave it. The main Cron UI already gates this exact value on `hasCronDeliverAll` (CronView.swift); Fleet skipped it.

NOT merge-introduced — pre-existing since FleetApplyExecutor landed (commit 2a32643, Phase-1 #4). Adjacent to the accepted "fleet cron-copy drops --repeat/--workdir/--no-agent fidelity" deferral — best addressed together as a single per-target, capability-aware cron-copy pass (resolve target caps once, then forward only the flags that host supports).
