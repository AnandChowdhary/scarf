## Description

Found by dogfooding the integrated build (2026-06-28): a new chat started from an upgraded project (stocker) had ZERO project context — the agent asked "what project?" The project's AGENTS.md managed block is correct on disk; it just isn't reaching the Hermes session.

ROOT CAUSE (source-verified against local Hermes v0.17): Hermes loads project context files (AGENTS.md) from the `hermes acp` PROCESS working directory — `agent/prompt_builder.py:build_context_files_prompt` defaults cwd to `os.getcwd()` and AGENTS.md is "cwd only"; `acp_adapter/session.py:_make_agent` does NOT pass the ACP `session/new` cwd into context loading (it only stamps `session_cwd` for the Codex runtime). Scarf passes the project path via the ACP `session/new` cwd (used by Hermes for TOOL working dirs) but spawns `hermes acp` WITHOUT setting the process cwd (`ProcessACPChannel`/`makeProcess` never set currentDirectoryURL) → process cwd = the GUI app's cwd (`/`) → no project AGENTS.md loads. NOT a merge regression — ScarfCore's ACP layer is unchanged by main's +51; it's a Hermes-behavior vs Scarf-assumption mismatch (ProjectAgentContextService assumed Hermes reads AGENTS.md from the session cwd).

FIX (Scarf-side, local + remote): spawn `hermes acp` with the process cwd = the project dir for project-scoped chats (one acp process per chat, so per-chat cwd is correct).
- ServerTransport: add `makeProcess(executable:args:cwd:)` (#if !os(iOS)) + default that ignores cwd.
- LocalTransport: set `proc.currentDirectoryURL` (guarded on fileExists → graceful).
- SSHTransport: prefix the remote cmd with `cd <remotePathArg(cwd)>; ` (graceful — runs from login dir if the dir is gone).
- ACPClient+Mac.forMacApp(projectCwd:) → makeProcess(cwd:).
- ChatViewModel.startACPSession passes its projectPath.

UPSTREAM follow-up (separate): Hermes ACP should inject context files from the `session/new` cwd (like cron's `--workdir`), not the process cwd.
