## Description

Audited 2026-06-28. The macOS project-context fix (forMacApp(projectCwd:) → SSHTransport.makeProcess prepends `cd <cwd>;`, commits b421280/5538e30) never reached iOS. ScarfGo spawns `hermes acp` from the SSH user's HOME, so Hermes loads context files (AGENTS.md/CLAUDE.md/.cursorrules) from home, NOT the project → agent never sees project instructions.

Key facts:
- Context files load from the PROCESS cwd of `hermes acp`, not the ACP session cwd (ACPClient+Mac.swift:16-18; SSHTransport.swift:447-454).
- iOS `ACPClient.forIOSApp` (Packages/ScarfIOS/Sources/ScarfIOS/ACPClient+iOS.swift:34) has no projectCwd; command at :78 = `PATH="…" [HERMES_HOME=…] exec hermes acp` (no `cd`). SSHTransport.makeProcess(cwd:) is `#if !os(iOS)`.
- iOS DOES write the block over SFTP (ProjectContextBlock.writeBlock, ChatView.swift:2211) and sets newSession(cwd: projectPath) (:2286) — neither triggers loading. Resume path (~:2419) uses cwd:home + forIOSApp.
- Misleading UI: project chip + branch + slash-commands + a write-failure banner all imply the agent has context when it doesn't.

Fix: add a `projectCwd: String?` param to forIOSApp → makeSSHExecChannel; when set, prepend `cd <quoted projectCwd>; ` to the command (SSHExecACPChannel doc line 57-58 anticipates this). Use `;` not `&&` (graceful degrade to home) and remotePathArg-style quoting (~/→$HOME/, quote spaces). Wire it through ChatController.startInternal (projectPath branch) and the resume path. Verify the profile `HERMES_HOME=` prefix still composes. Add a real test (assert the spawned command contains the cd prefix for a project chat; none for quick chat). See .memory/architecture/scarfgo-ios-does-not-load-project-context-process-cwd-gap.md
